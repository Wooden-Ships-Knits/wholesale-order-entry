## 1. Reps sign in by typing their first name

`/reps` used to open with a dropdown of all seven reps. It is now a text box:
a rep types **their first name** and their own password.

- Case and spacing are ignored — `aviva`, `AVIVA`, `  aVIVa ` all work.
- A **full name still works**, for anyone with the dropdown in their muscle
  memory.
- The server turns what was typed into the roster name
  (`reps_auth.resolve_name()`), and it is the roster name that goes in the
  session — every ownership lookup matches on it, so `"Aviva"` alone would find
  no orders.
- A first name shared by two reps resolves to **nobody**: both would have to
  type their full name. Guessing between them could drop a rep into a
  colleague's book, and the password check cannot catch that — it is checked
  against whichever name was guessed. A test pins that today's seven first names
  are unique, so adding a second Denise fails loudly instead of quietly
  disabling her sign-in.
- The failed-attempt throttle is now keyed on the **resolved rep**, so
  re-capitalising the name no longer buys a fresh set of guesses.

Nine tests in `backend/tests/test_reps_portal.py` cover this. The roster lives
in `REP_NAMES` (`backend/app/reps_auth.py`); `GET /api/reps-portal/names` still
exists for the office but the sign-in page no longer calls it.

## 2. Bounced signature emails are caught, on a timer

Two commits that only make sense together: one teaches the system to recognise a
bounce, the other makes it look without being asked.

### Recognising the bounce (#132)

`mailer.send_email` returning true only means Gmail **accepted** the message. A
wrong-but-valid address is accepted and then bounced minutes later. Until now
nothing read those bounces: `/admin` kept showing "Email Sent ✓ waiting for
signature", the five chasers fired for 30 days, and the rep was told to follow
up with a customer who had never received anything.

The inbound poller now recognises delivery-status notifications (RFC 3464):

- **Permanent failures only.** `5.x.x` means the address is wrong; `4.x.x` is a
  temporary defer the sending server is still retrying, and is ignored.
- A bounce carries none of our correlation tokens — it comes from the mail
  system, not the buyer — so it is matched by the short order id recovered from
  the original subject the notification quotes back.
- Stamping is **cleared when the request is re-sent**, so correcting the address
  resets the state.

In the admin table the **Signature** cell now shows
**"Undeliverable — check the address"**, with the mail server's own diagnostic
in the tooltip. That check runs *before* the "Email Sent ✓" branch, because both
are true at once — Gmail accepted the message before it bounced.

### Reading the mailbox without being asked (#134)

Recognising a bounce is worth nothing if nobody fetches it. Until now the
mailbox was only read when someone pressed **Check replies**, so a dead address
stayed invisible until a human went looking — which is how the problem above
survived as long as it did.

New setting **`POLL_REPLIES_MINUTES`** (default **5**) puts that on a timer, so
a bounce becomes a red row by itself. Rep replies to the conflict emails are
captured by the same sweep.

It is **off on development instances**, deliberately: dev and production read
the *same* `wholesale@` mailbox, and fetching marks messages `\Seen`, so an
automatic dev poll would silently consume the bounces and replies production is
waiting for. The **Check replies** button still works on dev, so a developer can
poll on purpose — it just never happens behind their back. Setting the value to
`0` disables the timer everywhere.

## 3. Show/hide eye on both password boxes

A shared `frontend/src/components/PasswordField.jsx`, used by the admin sign-in
and the rep sign-in, so the two cannot drift apart. Both passwords are typed
rarely and from memory, and a wrong one says only "Incorrect password" — being
able to look is the difference between one attempt and three, which matters now
that both logins are rate-limited.

It starts hidden on **every** mount: revealing is a deliberate act, never a
state that survives into the next person's session. The eye is `tabIndex={-1}`
so Tab goes from the password straight to **Sign in**, and carries an
`aria-label` so a screen reader can still reach it.

## 4. Payment cell warns before a card is destroyed

The card number exists in exactly one place — the encrypted admin-copy PDF —
and Accept/Decline destroys it. On 2026-08-10 an order was accepted before
anyone had keyed the number into Kugamon, and the number was gone for good.

Two guards now:

- The **Payment** cell is **yellow** while an unkeyed card copy still exists. An
  "Open card" chip on a yellow cell means there is still work to do there.
- The Accept confirmation says so before the click: *"the card number has not
  been opened yet. Accepting deletes it permanently — key it into Kugamon
  first."*

## 5. Bill To / Ship To fields are mandatory

These may no longer be left blank:

| Section | Required |
|---|---|
| Bill To | buyer name · street · city / state · zip · telephone |
| Ship To | street · city / state · zip · resale tax ID |

Validated **server-side** (`orders.py::_address_errors`) with the browser
mirroring it, and every blank field is reported at once rather than one per
round trip. The messages name the section — *"Bill To: street is required —
search for the billing address"* — because street/city/zip stay hidden until the
map search fills them, so a buyer who skipped the search has no visible empty
box to notice.

Ship To email is not on the list: it is already a required `EmailStr`, so a
missing one never reaches this check.

## 6. Day-6 phone-call nudge to the rep

The buyer is already chased on days 2, 5, 15, 22 and 29. This adds the one email
that goes to the **rep** instead — six days after the signing request, one day
after the buyer's second chaser, when it is clear the emails are not landing.
The reasoning in the code: by then a phone call from the person who wrote the
order is worth more than a sixth email to the same inbox.

- **Once per order, never repeated.** `rep_followup_sent_at` is stamped and
  committed *before* the send, so a crash costs the nudge rather than repeating
  it every hour.
- **Sent even when the address bounced** — unlike the buyer's chasers, which
  stop. A dead address is precisely when the rep most needs telling, because
  nothing will reach the buyer by email until someone corrects it.
- **Only live, unsigned, submitted orders**: a signing token that has not
  expired, no signature yet, status still `submitted`.
- **No rep address resolves?** The order is stamped anyway and logged — leaving
  it null would re-check that order every hour forever.
- The rep's copy carries the **card-masked order PDF** and, deliberately, **no
  signing link** — it is the buyer who signs, not the rep.
- Timing is `REP_FOLLOWUP_HOURS` (default **144** = 6 days); `0` disables it. It
  runs in the same hourly pass as the buyer's chasers.

The subject and body were supplied by Wooden Ships on 2026-08-10 and are to be
kept as written — it is the one subject with no short id on the end, because it
is addressed to a person being asked to pick up the phone rather than to file
it:

> ❗Pls CALL this account: `<store>` - `<season>`

## What changed in the data

**Three columns added to `orders`, across two migrations. Nothing renamed,
moved or dropped.** All three are nullable.

`0018_signature_bounce` (revises `0017_merge_heads`):

| Column | Type | Holds |
|---|---|---|
| `signature_bounced_at` | `timestamptz` | when the signature request bounced |
| `signature_bounce_reason` | `text` | what the mail server said ("Address not found") |

`0019_rep_followup` (revises `0018_signature_bounce`):

| Column | Type | Holds |
|---|---|---|
| `rep_followup_sent_at` | `timestamptz` | when the day-6 nudge went to the rep; null = not yet |

Both `downgrade()`s drop what they added, so the pair is reversible. All three
are timestamps rather than flags on purpose — "when did it happen" is worth
answering, and nulling one re-arms the behaviour if a request is sent afresh.

**API.** The admin order row gained `signatureBouncedAt` and
`signatureBounceReason`. The **rep** payload was deliberately not touched —
`_rep_row()` still emits exactly the key set `test_reps_portal.REP_ROW_KEYS`
pins, with no card, conflict, certificate or Salesforce fields.

**Table columns: unchanged today.** Both tables keep yesterday's headers; the
new information rides inside the existing Signature and Payment cells. For the
record, the recent column changes were on **2026-08-10**, not in this release:
"Total Amount" → **Value** (moved beside Account Name), "Quantity" → **QTY**,
"Shipping Window" → **Ship Window**, and the rep Order ID became a link to that
order's masked PDF. The rep table therefore reads:

> Date · Order ID · Signature · Season · QTY · Ship Window · Account Name ·
> Value · Written By · Sales Territory · Notes · Decision

## Deploying this release

Nothing manual. Rebuild each stack from `main`; both migrations apply
themselves, because the backend image starts with
`alembic upgrade head && uvicorn app.main:app …`.

Two new settings ship with this release, both with working defaults, so `.env`
needs no edit unless you want to change them: `POLL_REPLIES_MINUTES` (5) and
`REP_FOLLOWUP_HOURS` (144). Set either to `0` to switch that behaviour off.

```bash
# on the VM
cd ~/wholesale-order-entry
git checkout main && git pull
docker compose up -d --build                                    # production
docker compose -f docker-compose.dev.yml --env-file .env.dev up -d --build   # dev
```

The two stacks have separate databases (volumes `pgdata` and `pgdata_dev`), so
each migrates itself on its own restart. To confirm by hand:

```bash
docker compose exec backend alembic current   # expect 0019_rep_followup (head)
```

Because the migration runs *before* uvicorn, a backend that cannot reach its
database never starts and restarts in a loop instead. If that happens,
`docker logs <container>` shows whether it died in the migration step.

Then check:

- [ ] `/reps` shows a **first name** box, not a dropdown, and the eye appears on
      the password
- [ ] `/admin` sign-in has the eye too
- [ ] An order with an unkeyed card shows a **yellow** Payment cell
- [ ] Submitting the order form with an empty Bill To telephone is refused, and
      the message names the field
- [ ] The backend log shows the hourly pass running — the day-6 rep nudge rides
      in it, so nothing extra to start
- [ ] `curl -s <site>/api/health` → `"env":"production"` on production,
      `"dev":true` on dev

## Signing in

**Usernames — reps type their first name** (case and spacing don't matter):

| Rep | Types |
|---|---|
| Aviva Landin | `aviva` |
| Denise Arnett | `denise` |
| Jason Hilsenrad | `jason` |
| Kitty Tally | `kitty` |
| Michael Young | `michael` |
| Rande Cohen | `rande` |
| Vickie Wilde | `vickie` |

**Passwords are not written down here, and cannot be.** They exist only as
one-way PBKDF2 hashes in `REPS_PASSWORD_HASHES` (`.env`, which never enters
git) — there is nothing to copy out, only something to reset. Keep the plaintext
list wherever the office already keeps credentials, never in this repository.
`/admin` is one shared password in `ADMIN_PASSWORD_HASH`, same rule.

**Changing one rep's password** — this reads the current map from the running
container, so the other six cannot be dropped. Note the leading space, which
keeps the password out of your shell history:

```bash
 docker compose exec -T backend python -c '
import json, os
from app.admin.security import hash_password
from app.reps_auth import normalize_name
h = json.loads(os.environ["REPS_PASSWORD_HASHES"])
h[normalize_name("Kitty Tally")] = hash_password("HER-NEW-PASSWORD")
print("REPS_PASSWORD_HASHES=" + json.dumps(h, separators=(",", ":")))
'
```

Paste the printed line over the existing `REPS_PASSWORD_HASHES=` line in `.env`,
then `docker compose up -d backend` — a plain `restart` does not re-read the env
file. Verify with a login: the new password returns `{"ok":true,…}`, the old one
`Incorrect name or password`.

Do **not** use `python -m app.reps_auth "Kitty Tally=…"` for a single rep: it
prints a complete `REPS_PASSWORD_HASHES` value containing *only* that rep, and
pasting it locks the other six out. It is for setting all seven at once.

A rep must appear in **both** `REP_NAMES` and the hash map, so removing a
departing rep from the roster locks them out even if their hash is still in
`.env`.
